Audit Task: DCircles Real-Time Data Architecture (Read-Only Audit First, No Code Changes Yet)

Before making any code changes, perform a complete architectural audit of the DCircles system. Do not modify any files until the audit is complete and the current implementation is fully understood.

Objective

Verify that the application has one continuously running, real-time market data engine that serves as the single source of truth for all DCircles.

DCircles exist in only three places:

Chart
AI Bots
DCircles page

All three should always display the same market statistics at the same moment.

Audit Requirements
1. Source of Truth

Identify exactly where each DCircles currently obtains its data.

Determine whether:

Chart DCircles
AI Bot DCircles
DCircles page

all read from the same shared store, or whether any of them still maintain separate tick buffers, separate stores, or independent calculations.

List every source of market data used.

2. Continuous Market Engine

Verify whether the market data engine runs continuously.

The market engine should:

continue receiving ticks even when no bot is running
continue updating when no charts are open
continue updating when no trades are active
never stop simply because the UI changes

A user should be able to log in at any time and immediately see live DCircles statistics without waiting for the history to build.

Identify anything that causes tick collection or DCircles updates to stop.

3. Synchronization

Determine whether all three DCircles always show identical:

percentages
digit frequencies
tick counts
last digits
history

If differences can occur, identify exactly why.

4. Shared Calculations

Confirm whether digit percentages are calculated once centrally or recalculated independently by each interface.

The preferred architecture is:

One tick stream → One shared store → One shared calculation → Three synchronized UI views.

Identify any duplicate calculations.

5. Tick History

Audit the rolling tick-history implementation.

Confirm:

current default size
maximum allowed size
whether the rolling buffer is actually capped
whether old ticks are discarded correctly

The desired architecture is:

default history: 1000 ticks
maximum stored history: 3000 ticks
rolling buffer only (never grows indefinitely)
6. Cross-Session Consistency

Determine what happens when:

a user refreshes
opens another tab
logs in from another device

Explain how DCircles history is initialized in each case.

If users can end up with different percentages because they started collecting ticks at different times, identify the cause and propose the best architecture to minimize this divergence.

Do not implement anything yet—just audit and explain.

7. Performance

Verify:

one WebSocket subscription per symbol
no duplicate subscriptions
no duplicate tick buffers
no unnecessary recomputation
no memory leaks
no stale subscribers
Deliverables

Provide a detailed audit containing:

Current DCircles architecture.
Every source of tick data.
Whether all three DCircles truly share one store.
Whether the market engine runs continuously.
Whether percentages remain synchronized in real time.
Whether the rolling history is correctly capped.
Any inconsistencies or architectural weaknesses found.
A recommended implementation plan to ensure:
one shared store,
continuously updating real-time data,
identical percentages across Chart, AI Bots, and the DCircles page,
a rolling history capped at 3000 ticks with a 1000-tick default.

Important: This is an audit only. Do not modify code or push changes until the audit is complete and the findings are presented.
