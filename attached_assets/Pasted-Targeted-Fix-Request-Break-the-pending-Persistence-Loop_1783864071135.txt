Targeted Fix Request — Break the __pending__ Persistence Loop

Confirmed Root Cause

The issue is no longer a mystery.

The runtime logs prove that localStorage['active_loginid'] already contains '__pending__' before the app starts.

The current code then:

Reads it via AuthSessionManager.getAuthInfo().

Treats it as a valid login ID because it is a non-empty string.

Passes it through AccountModeController.restoreFromUrl().

Rewrites it back via AuthSessionManager.setActiveAccount().

Uses it in the OTP endpoint and WebSocket authorize flow.

Fix Objective

Do not redesign the auth system.

Do not add new authentication logic.

Simply prevent invalid account IDs from entering or persisting in the canonical auth state.

Required Changes
1. Validate account IDs in getAuthInfo()
Required

When reading active_loginid from localStorage:

Accept only real Deriv login IDs.

Reject sentinel values such as __pending__.

Reject malformed values that do not match a valid account pattern.

If invalid, return null for accountId.

2. Prevent invalid values from being persisted
Required

In setActiveAccount(loginid, token):

Persist active_loginid only if the login ID is valid.

Do not write __pending__.

Do not write malformed account IDs.

3. Self-heal existing stale storage
Required

If getAuthInfo() detects an invalid active_loginid:

Remove it from localStorage immediately.

Log a warning indicating that a stale invalid account ID was cleaned up.
