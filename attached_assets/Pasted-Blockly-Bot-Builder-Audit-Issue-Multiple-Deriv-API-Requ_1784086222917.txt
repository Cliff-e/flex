Blockly Bot Builder Audit
Issue: Multiple Deriv API Request Failures
Executive Summary

The bot builder is successfully connecting to Deriv and receiving market data, but several requests being generated by the Blockly runtime are invalid or outdated.

The console shows four different categories of failures:

Purchase request contains unsupported parameters.
Balance request uses an invalid schema.
Several API calls no longer exist.
Contract purchase payload is built incorrectly.

These indicate that the Blockly engine is still using legacy request builders while the rest of the application already uses the newer Deriv API.

Evidence
1. Purchase Request

Console shows

{
  "buy":"1",
  "price":0.35,
  "parameters":{
      "amount":0.35,
      "basis":"stake",
      "contract_type":"DIGITOVER",
      "currency":"USD",
      "duration":1,
      "duration_unit":"t",
      "symbol":"1HZ100V",
      "selected_tick":1,
      "barrier":"1"
  }
}

Response

InputValidationFailed

Properties not allowed:
symbol
Root Cause

The purchase request builder is assembling a payload that does not match Deriv's current buy schema.

The API is rejecting the parameters object before the trade is sent.

This is not a WebSocket issue.

This is a request serialization issue.

Audit Required

Locate where Blockly converts blocks into a Buy request.

Search for

buy:
purchase:
contract_type:
parameters:
selected_tick
symbol

Find every place where the parameters object is assembled.

Verify against the latest Deriv API documentation.

Do not hardcode fields.

Generate parameters only from the proposal response.

2. Balance Request

Console

{
 balance:1,
 subscribe:1,
 account:"all"
}

returns

InputValidationFailed
Root Cause

The API no longer accepts

account:"all"

for balance subscriptions.

Current balance requests should simply be

{
    "balance":1,
    "subscribe":1
}

or use loginid after authorization if required.

Audit

Find

balance:1
account:"all"

Replace with the supported schema.

4. Purchase Payload Contains Manual Parameters

The request currently manually inserts

symbol

duration

barrier

contract_type

selected_tick

basis

currency

into

parameters

This is risky.

The Proposal response already contains the authoritative contract specification.

The purchase should be generated from the proposal returned by Deriv instead of rebuilding the contract manually.

Recommendation

Current flow

Blockly
      ↓
Build contract manually
      ↓
buy

Recommended

Blockly
      ↓
proposal()
      ↓
proposal.id
      ↓
buy(proposal.id)

Only stake/price should be supplied during buy.

Everything else should originate from the proposal.

5. API Version Drift

The project now has three independent systems.

Main trading engine

Bot Builder

Blockly runtime

Each appears to build Deriv requests independently.

That almost always causes request drift.

Recommendation

Create one shared module.

DerivApiService

├── proposal()

├── buy()

├── sell()

├── balance()

├── authorize()

├── ticks()

└── portfolio()

Every feature should call this service.

Never construct raw JSON inside Blockly generators.

6. Error Handling

Current behavior

API Error

↓

console.error(object)

Users only see

Input validation failed

with no indication of which field caused the error.

Instead expose

API Request

API Response

Validation Error

Request Builder

Generated Blockly JSON

This will reduce debugging time dramatically.

Final Assessment

The WebSocket connection is working correctly, and authentication appears successful. The failures stem from the Blockly runtime generating outdated or malformed Deriv API requests. The bot builder should be refactored to use a single shared Deriv API service, with all purchase requests based on proposal IDs rather than manually constructed parameter objects. This will eliminate the validation errors, prevent API version drift, and make future maintenance much easier.
