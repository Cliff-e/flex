# VIRTUAL HOOK — EXECUTION SPECIFICATION

You are implementing the Virtual Hook finishing work in an existing React/TypeScript trading application.

Phase 0 reconnaissance and the existing VH architecture have already been established.

**Do not restart broad repository reconnaissance.**

Inspect the existing implementation and the relevant immediate dependencies, then implement the requirements below.

The most important correction to previous specifications is:

> Virtual Hook has THREE independent authorization conditions, and EACH condition has its own Enable/Disable control inside VH Settings.

The three conditions are:

1. Maximum consecutive virtual wins before real purchase
2. Maximum consecutive virtual losses before real purchase
3. Maximum number of Virtual Hook instances/steps before real purchase

The user may enable any combination of these three.

Authorization occurs when **ANY ENABLED condition reaches its configured threshold**.

---

# 1. CORE PRODUCT BEHAVIOR

Virtual Hook is a simulation layer that runs BEFORE real trading.

It is not a second trading account.

The intended flow is:

```text
LIVE MARKET TICKS
        ↓
existing strategy/signal conditions
        ↓
VH intercepts the signal
        ↓
VH virtual contract starts
        ↓
REAL-TIME LIVE TICKS CONTINUE ARRIVING
        ↓
virtual entry tick
        ↓
duration ticks arrive in real time
        ↓
virtual exit tick
        ↓
existing settlement logic
        ↓
VIRTUAL WIN or VIRTUAL LOSS
        ↓
update VH counters
        ↓
check enabled authorization conditions
        ↓
if threshold reached:
        VH authorization reached
        ↓
CURRENT VH CONTRACT REMAINS VIRTUAL
        ↓
VH turns OFF / latch is released for future signals
        ↓
NEXT UNLATCHED SIGNAL
        ↓
REAL BUY
```

The current VH contract that causes authorization is NEVER converted into a real trade.

# 5. CONTROL 3 — MAX VIRTUAL HOOK INSTANCES / STEPS

This is the third authorization condition.

DO NOT remove the existing concept of `maxSteps`.

Instead, correct its meaning.

It represents:

> Maximum number of completed Virtual Hook contract instances allowed before VH authorizes the next real trade.

Configuration:

```ts
maxSteps: number
maxStepsEnabled: boolean
```

It counts ALL completed VH instances regardless of outcome.

For example:

```text
maxSteps = 5
maxStepsEnabled = true
```

Sequence:

```text
VH #1 → WIN
VH #2 → LOSS
VH #3 → LOSS
VH #4 → WIN
VH #5 → WIN
```

After VH #5 settles:

```text
VIRTUAL INSTANCE LIMIT REACHED
```

Authorization occurs.

Again:

**VH #5 remains virtual.**

It is NOT converted into a real purchase.

Then:

```text
VH OFF
↓
NEXT UNLATCHED SIGNAL
↓
REAL BUY
```

The step condition is therefore different from the win/loss conditions:

```text
WIN CONDITION
→ consecutive wins

LOSS CONDITION
→ consecutive losses

STEP CONDITION
→ total completed VH instances in the current VH authorization session
```

# 6. THE THREE CONDITIONS ARE OR CONDITIONS

Authorization is:

```text
ANY ENABLED CONDITION REACHES ITS THRESHOLD
```

Equivalent logic:

```ts
if (
    winThresholdEnabled &&
    winThreshold > 0 &&
    consecutiveVirtualWins >= winThreshold
) {
    return AUTHORIZED;
}

if (
    lossThresholdEnabled &&
    lossThreshold > 0 &&
    consecutiveVirtualLosses >= lossThreshold
) {
    return AUTHORIZED;
}

if (
    maxStepsEnabled &&
    maxSteps > 0 &&
    virtualInstances >= maxSteps
) {
    return AUTHORIZED;
}

if (
    consecutiveTechnicalFailures >= maxConsecutiveFailures
) {
    return STOPPED;
}

return RETRY;
```

Use the project's existing enums/result types where appropriate.

# 7. ZERO SEMANTICS

Zero must mean:

```text
DISABLED
```

for the numeric threshold.

Do NOT normalize zero to one.

Do NOT use:

```ts
Math.max(1, value)
```

for these authorization thresholds.

Valid examples:

```text
Wins:
0

Losses:
0

Steps:
0
```

A value of zero means that condition does not authorize VH.

The explicit Enable/Disable switch is the primary user-facing control, but zero must also safely behave as disabled.

Therefore:

```text
wins = 0
losses = 0
steps = 0
```

must never cause immediate authorization.

# 10. VIRTUAL INSTANCE COUNTER

Maintain a separate session counter:

```ts
virtualInstanceCount
```

Every successfully completed VH contract increments it:

```text
VH #1 → virtualInstanceCount = 1
VH #2 → virtualInstanceCount = 2
VH #3 → virtualInstanceCount = 3
```

It increments regardless of whether the contract was:

```text
WIN
```

or:

```text
LOSS
```

A technical failure is NOT a completed VH instance unless the existing architecture explicitly treats it as a settled virtual contract.

Do not count technical failures as wins/losses.

Do not use the step counter as a replacement for the win/loss streak counters.

---

# 11. TECHNICAL FAILURES REMAIN SEPARATE

Do not confuse:

```text
VALID VIRTUAL LOSS
```

with:

```text
TECHNICAL FAILURE
```

A virtual loss means the simulated contract actually settled and lost.

Technical failures include things such as:

* proposal failure
* request failure
* timeout
* execution infrastructure failure
* other existing technical failures

Keep:

```ts
consecutiveTechnicalFailures
maxConsecutiveFailures
```

separate.

The three user authorization conditions are:

```text
win streak
OR
loss streak
OR
virtual instance count
```

Technical failure is a separate safety mechanism:

```text
technical failure streak
        ↓
STOPPED
```

Do not merge these concepts.

# 12. RESET BEHAVIOR


A new VH session must never inherit an old win streak, loss streak, or step count.

# 13. REAL-TIME LIVE TICK REQUIREMENT — CRITICAL

This is one of the most important requirements.

VH must simulate a contract **in real time**.

It must behave like a real trade watching the live market.

The production architecture remains:

```text

        ↓
AITickObserver
        ↓
VirtualHookEngine
        ↓

        ↓

        ↓

        ↓

        ↓

        ↓
settlement
```

Do NOT implement VH as:

```text

↓

↓
simulate outcome instantly
```

Do NOT use historical tick replay.

Do NOT use random values.

Do NOT generate synthetic ticks.

Do NOT create a fake timer that pretends ticks occurred.

# 14. WHAT "REAL-TIME" MEANS

When VH starts a virtual contract:

### Entry

Wait for the appropriate live tick from the existing live tick stream.

Record the actual live entry spot/digit.

Then the VH contract is considered active.

### During contract

Wait for actual live ticks arriving from:

```text
PublicTickManager
```

through:

```text
AITickObserver
```

Consume them according to the configured contract duration.

### Exit

When the correct live duration tick arrives:

Record the actual live exit spot/digit.

### Settlement

Use the existing settlement implementation.

Calculate:

```text
entry spot
exit spot
entry digit
exit digit
contract condition
WIN / LOSS
virtual stake
virtual payout
virtual profit/loss
```

Only AFTER the virtual contract has genuinely settled should:

```text

loss streak
instance count
```

be updated.

Then evaluate the three enabled authorization conditions.
