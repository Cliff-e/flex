The root cause has been identified.

Current behavior

The browser has:

logged_state=true

but no REST access token and no active_loginid.

useOauth2.ts sets:

isSingleLoggingIn = true

because:

loggedState === 'true'
&& !isClientAccountsPopulated

The Header then renders AccountsInfoLoader instead of the Login button:

isSingleLoggingIn &&
!is_tmb_enabled &&
!hasRestAuth

The application becomes permanently stuck because the old requestSessionActive() resolver was removed/commented out.

As a result:

Login button never renders
initiateDerivAuth() is never called
/api/auth/login is never requested
OAuth never starts
User is trapped forever behind the loading spinner
Objective

Do not remove silent SSO.

Instead, make it fail gracefully.

The intended behavior should be:

If a valid REST session exists → continue silent login.
If silent login succeeds → proceed normally.
If silent login cannot recover a session (missing access token, stale cookie, timeout, or failure) → exit SSO mode, clear stale state, and render the Login button.
Required implementation
1. Centralize stale-session detection

Create a helper (or equivalent) that determines whether the browser is pretending to be logged in:

logged_state === "true"
&& !AuthSessionManager.isAuthenticated()

This represents a stale browser session.

2. Recover instead of hanging

In useOauth2.ts, after entering the SSO path:

Attempt silent recovery.

If recovery succeeds:

setIsSingleLoggingIn(false)
continue authenticated flow

If recovery fails (or no recovery mechanism exists):

clear stale auth markers
setIsSingleLoggingIn(false)

Do not leave the component permanently waiting.

3. Clear only stale browser state

Only when all of these are true:

logged_state=true
AND
no REST access token
AND
no valid active_loginid

clear only the stale login markers.

Do not delete valid tokens.

Do not log the user out if a real authenticated session exists.

4. Ensure Login button becomes reachable

After stale recovery:

isSingleLoggingIn === false

Header must naturally fall through to:

<LoginButton />

No hacks.

No forced rendering.

No bypassing existing logic.

5. Preserve successful OAuth

Do not change:

CallbackPage
PKCE flow
AuthSessionManager token storage
Account selection
DO OAuth endpoints
WS authorization

Those are already correct.

Only fix the state machine that prevents OAuth from starting.

6. Add temporary diagnostics

Add logs:

[SSO]
entered silent login

[SSO]
attempting recovery

[SSO]
recovery succeeded

[SSO]
recovery failed

[SSO]
stale browser session detected

[SSO]
clearing stale browser markers

[SSO]
leaving silent login

[HEADER]
rendering Login button

These logs should be removable after verification.

7. Verification criteria

After the fix:

Scenario A
Fresh visitor

Expected:

Login button visible

Scenario B
Valid authenticated session

Expected:

silent login succeeds

Scenario C
Stale cookie

Current state:

logged_state=true
accessToken missing
active_loginid missing

Expected:

[SSO] stale browser session detected
[SSO] clearing stale browser markers
[SSO] leaving silent login

Immediately afterward:

Login button appears

Clicking Login must produce:

GET /api/auth/login
→ DigitalOcean backend
→ auth.deriv.com
→ callback
→ /api/auth/exchange
→ /api/auth/accounts
→ AuthSessionManager.setActiveAccount(real loginid)
→ authenticated dashboard

Do not implement a workaround that simply forces isSingleLoggingIn = false on startup. The fix must preserve the intended silent-login behavior while ensuring stale sessions always recover back to an interactive login state.
